Isley API v1

A JSON API for your grow journal: plants, strains, zones, sensors and everything you log against them.

This page is the guide. The full reference, every endpoint, field and error, is the OpenAPI 3.1 document at /api/v1/openapi.yaml. Load it into any OpenAPI tool (Swagger Editor, Postman, Insomnia, an SDK generator) for a browsable reference.

Getting started

Create a key in Settings → API and pick what it may do. Then ask the instance about itself:

export ISLEY=https://isley.example
export ISLEY_KEY=...   # the key, shown once when you create it

curl -H "Authorization: Bearer $ISLEY_KEY" $ISLEY/api/v1/instance
{
  "version": "2.6.0",
  "time_zone": "America/New_York",
  "now": "2026-11-11T22:28:49-05:00",
  "guest_mode": false,
  "features": {"ac_infinity": true, "ecowitt": false, "sensor_ingest": true,
               "cannadb": false, "stream_capture": false, "mcp": true},
  "api": {"key_name": "my script", "scopes": ["write"]}
}

time_zone is the zone your times are read and written in (see Dates and times), and api.scopes is what this key may do.

Keys and access

Every request needs a key, sent as Authorization: Bearer <key>. X-API-KEY: <key> is accepted too, for older clients. A logged-in browser session doesn't count, and guest mode doesn't open the API.

AccessCan
readRead everything.
writeRead, and record: create and edit plants, log activities and measurements, add images and smoke reports, edit strains and breeders, adjust seed counts.
adminEverything, including deleting plants, strains and breeders, and managing zones, sensors and streams.
ingestPush sensor readings to /api/sensors/ingest. Separate from the levels above; a key can have both.

A missing or unknown key gets 401 unauthorized. A key without the access a request needs gets 403 insufficient_scope, with the access it needed in details.required. Writes are logged on the server with the key's name, so give each script or device its own key.

Conventions

  • JSON in and out (Content-Type: application/json), except image uploads, which are multipart/form-data.
  • Resources are plural nouns: GET /plants, GET /plants/{id}, POST /plants, PATCH /plants/{id}, DELETE /plants/{id}. Things that belong to a plant live under it (/plants/{id}/activities). Actions that aren't plain edits get their own resource, such as POST /plants/{id}/status.
  • PATCH changes only the fields you send. Sending null clears a field that may be empty.
  • Creating returns 201 with the new resource and a Location header; editing returns 200 with the resource as it now stands. No second call is needed to read it back.
  • References carry names as well as ids, such as "zone": {"id": 2, "name": "Tent"}, so you can show them without another call.
  • Numbers with units say so in the field name (harvest_weight_g) or carry a unit field (sensors, measurements).
  • Plant age, days since watering and feeding, day of flower and the estimated harvest are worked out by the server, in the instance zone. Don't recompute them.

Dates and times

  • Instants (when something happened) are RFC 3339 with an offset: 2026-11-11T21:00:00-05:00. Responses always use the instance zone's offset.
  • An instant you send without an offset (2026-11-11T21:00) is read in the instance zone. Send an offset or Z if you mean another zone.
  • Calendar days (a plant's start_date, an image's day) are plain YYYY-MM-DD. They have no time and are never shifted.
  • A plant's start day is day 1, and week 1 is days 1–7.
  • Day filters such as GET /activities?from=2026-11-10&to=2026-11-10 mean whole days in the instance zone, both ends included.

Errors

Every error has the same shape. code is stable and meant for programs; message is for people.

HTTP/1.1 404 Not Found
{"error": {"code": "plant_not_found", "message": "plant 999 does not exist"}}

HTTP/1.1 400 Bad Request
{"error": {"code": "invalid_request", "message": "the request has invalid fields",
           "details": {"fields": {"activity_type_id": "99 does not exist"}}}}
StatusCodes
400invalid_request: details.fields names each bad field.
401 / 403unauthorized, insufficient_scope
404plant_not_found, strain_not_found, ... and not_found for an unknown path
409The request conflicts with what's stored, for example name_taken, zone_not_empty or idempotency_key_reused
413payload_too_large
500 / 503internal_error, unavailable. Retrying later is safe for reads, and for writes sent with an Idempotency-Key.

Lists and paging

Lists answer {"items": [...], "next_cursor": "..."}. Ask for up to 200 at a time with limit (default 50). While next_cursor isn't null, pass it back as cursor for the next page. Cursors are opaque: don't build or edit them.

curl -H "Authorization: Bearer $ISLEY_KEY" "$ISLEY/api/v1/plants?phase=growing&limit=100"
curl -H "Authorization: Bearer $ISLEY_KEY" "$ISLEY/api/v1/plants?phase=growing&limit=100&cursor=eyJhZnRlcl9pZCI6MTAwfQ"

Safe retries

A script on a flaky connection can't tell whether a POST that timed out was recorded. Send an Idempotency-Key header (any unique string up to 255 characters, such as a UUID) with each POST. If you retry with the same key and the same body, you get the first response back, marked Idempotent-Replayed: true, and nothing is recorded twice. Reusing a key for a different request gets 409 idempotency_key_reused. Keys are remembered for 24 hours, per API key.

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -H "Idempotency-Key: 3f6c1d0e-water-2026-11-11" \
     -d '{"activity_type_id": 1, "note": "250 ml"}' \
     $ISLEY/api/v1/plants/12/activities

Recipes

What's growing, and when was it last watered?

curl -H "Authorization: Bearer $ISLEY_KEY" "$ISLEY/api/v1/plants?phase=growing"

Each plant carries age (day, week), status, days_since_watered, days_since_fed, flower (with its day count) and estimated_harvest_date. GET /plants/{id} adds the status history, days per stage, sensors with their latest readings, and recent activities and measurements.

Log a watering

Find the activity type ids once with GET /activity-types (Water, Feed and Note are built in; types you added in Settings are there too).

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -d '{"activity_type_id": 1, "note": "250 ml, pH 6.3", "at": "2026-11-11T21:00"}' \
     $ISLEY/api/v1/plants/12/activities
{"id": 8, "plant": {"id": 12, "name": "Agent Test"}, "activity_type": {"id": 1, "name": "Water"},
 "note": "250 ml, pH 6.3", "at": "2026-11-11T21:00:00-05:00",
 "is_watering": true, "is_feeding": false, "measurements": []}

Leave out at to mean now. To water a whole tent in one call, use POST /activities/bulk with "plant_ids": [12, 13, 14]. An activity type that records amounts takes them as "measurements": [{"metric_id": 3, "value": 250}].

Record a measurement

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -d '{"metric_id": 1, "value": 31.5}' \
     $ISLEY/api/v1/plants/12/measurements

GET /metrics lists the metrics and their units.

Move a plant to flower

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -d '{"status_id": 5, "at": "2026-11-11T08:00"}' \
     $ISLEY/api/v1/plants/12/status

It answers 201 with the new status entry, or 200 with "changed": false if the plant already had that status. Status ids are in GET /statuses. Record a harvest weight with PATCH /plants/{id} and {"harvest_weight_g": 112.5}.

Start a plant

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -d '{"name": "Lady 3", "strain_id": 4, "zone_id": 2, "status_id": 3,
          "start_date": "2026-11-11", "decrement_seed_count": true}' \
     $ISLEY/api/v1/plants

How did the tent do overnight?

Find the zone's sensors with GET /zones/{id}, then summarise one over a range. The bucket can be a size (15m, 1h, 1d) or raw for every reading. Leave it out and a size is picked for the range.

curl -H "Authorization: Bearer $ISLEY_KEY" \
     "$ISLEY/api/v1/sensors/2/data?from=2026-11-10T20:00&to=2026-11-11T08:00&bucket=1h"
{"sensor": {"id": 2, "name": "Tent Temperature", "type": "Temperature", "unit": "°F"},
 "from": "2026-11-10T20:00:00-05:00", "to": "2026-11-11T08:00:00-05:00", "bucket": "1h",
 "items": [{"start": "2026-11-10T20:00:00-05:00", "min": 69.5, "avg": 69.96, "max": 70.44, "count": 12}, ...],
 "next_cursor": null}

Fans, lights and other on/off ports also report on_fraction (the share of readings that were on) and starts (how often they switched on) per bucket.

Add a pack of seeds

curl -H "Authorization: Bearer $ISLEY_KEY" -H "Content-Type: application/json" \
     -d '{"delta": 10}' $ISLEY/api/v1/strains/4/seed-count

A delta adds or removes seeds without overwriting a change someone else made at the same time. The count never goes below 0.

Upload a photo

curl -H "Authorization: Bearer $ISLEY_KEY" \
     -F "image=@canopy.jpg" -F "taken_on=2026-11-11" -F "description=week 3 of flower" \
     $ISLEY/api/v1/plants/12/images

One JPEG, PNG, GIF or WebP per request.

AI assistants (MCP)

Isley can also serve AI assistants such as Claude over the Model Context Protocol, at /mcp. Turn on Enable MCP server in Settings → API, then connect with a key. The assistant gets that key's access: a read key can answer questions, and a write key can also log waterings and start plants. There are no delete tools.

claude mcp add --transport http isley $ISLEY/mcp --header "Authorization: Bearer $ISLEY_KEY"

The README has the Claude Desktop setup and the list of tools.
